## 4. Financing과 기존 ERP의 관계

Financing은 별도 ERP가 아니다.

기존 MXMN의 다음 기능을 계속 System of Record로 사용한다.

- 매입
- LOT
- 재고
- 매출
- 출고
- 입금
- 지급
- 거래처원장

Financing은 그 위에 다음 업무를 연결한다.

- 계약
- 계약상품
- 계약책임
- 계약조건
- 계약문서
- 실제 원가정산
- Financing 기간비용
- 출고정산
- 입금요청/입금확인
- 보증금
- 최종정산

Financing 전용으로 재고, SALE, RECEIPT, PAYMENT 원장을 중복 생성하지 않는다.

`MXMN_FinSales`는 Reference Implementation으로만 유지한다. 기존 FinSales의 7.5%, 0.9원/kg·일 등의 값은 전체 계약에 적용되는 고정값이 아니며 **실제 개별 계약서 조건이 기준**이다.

## 5. Phase 1 핵심 업무모델

가장 중요한 전제는 **계약이 LOT보다 먼저 존재할 수 있다**는 것이다.

실제 업무의 일반적인 순서는:

계약  
→ 계약상품/계약수량/계약조건  
→ 수입 또는 국내매입  
→ 실제 비용 발생  
→ 통관/입고  
→ 최초 원가정산  
→ ERP LOT 생성  
→ 계약과 LOT 연결  
→ Financing 기간  
→ 일일/부분출고  
→ 반복 정산  
→ 최종출고  
→ 최종 계약마감

이다.

따라서 Phase 1에서 다음 관계를 도입하였다.

```text
Contract
  └─ Contract Item 1..N
       └─ ERP LOT 0..N
```

핵심 원칙:
- LOT 없이 계약 생성 가능
- 한 계약에 복수 계약상품 가능
- 계약상품과 계약수량은 LOT와 독립
- 한 계약상품에 실제 ERP LOT 여러 개 후행 연결 가능
- 기존 `tb_fin_contract_lot`은 실제 LOT 연결구조로 유지

## 7. 계약번호

DB 내부 PK와 업무용 `contract_no`는 분리한다.

계약번호는 사용자가 직접 입력하지 않고 자동생성한다.

업무번호에는 회사, 계약일, 계약업체, 계약유형, 순번/식별정보 등을 반영하여 사람이 보았을 때 주요 내용을 식별할 수 있도록 한다.

`contract_no`는 Unique이며 확정 후 일반 수정으로 임의 변경하지 않는 것이 원칙이다.

## 10. 최초 계약업체와 실제 출고업체

최초 계약업체는 계약의 1차 책임주체이다.

실제 출고업체는 최초 계약업체와 다를 수 있다.

추가 출고업체는 특별출고약정 수취 후 출고할 수 있다.

그러나 실제 ERP의 다음 거래는 **실제 출고업체 기준**이다.

- SALE
- 매출채권
- 입금
- 거래명세표
- 계산서/세금계산서

즉 **계약상 책임주체와 실제 거래주체를 분리**한다.

---

## 11. 입금확인 원칙

Financing 기본 흐름:

```text
정산금액 산정
→ 입금요청
→ 실제 은행입금 확인
→ 출고
```

원칙적으로 미수 없이 입금을 받고 출고한다.

그러나 실제 은행입금은 먼저 이루어지고 ERP RECEIPT 등록은 나중에 일괄 처리할 수 있으므로 **RECEIPT 전산등록을 출고의 Hard Guard로 사용하지 않는다.**

향후 별도의 간단한 `입금확인` 절차를 둔다.

---

## 12. 보증금 향후 설계

현재 Phase 1의 `deposit_required / deposit_amount`는 계약 당시의 보증금 조건이다.

실제 보증금 이동은 향후 별도의 **Deposit Ledger / History**로 관리한다.

필요 업무:

```text
보증금 수취
→ 계약/BL별 배정
→ 배정해제
→ 다른 계약/BL로 재배정
→ 반환
```

하나의 보증금을 여러 계약 또는 여러 BL에 분산 배정할 수 있어야 한다.

관리대상:
- 최초 수취액
- 현재 잔액
- 계약/BL별 배정액
- 가용액
- 반환액
- 재배정 내역
- History/Audit

계약 종료 시 보증금을 반드시 반환하는 구조로 고정하지 않는다. 다른 계약의 담보로 재배정할 수 있다.

## 13. 2026-10-06 Migration 결함과 해결

V1 보완 Migration을 MXMN-WORK 로컬 SQL Server에서 실제 실행했을 때 다음 오류가 발생하였다.

```text
SQL Server error 207
Invalid column name 'contract_item_id'
```

원인은 동일 `conn.execute(text(...))` batch에서:

1. `ALTER TABLE ... ADD contract_item_id`
2. FK/INDEX 생성
3. legacy Contract Item 보정
4. `contract_item_id` 참조 UPDATE

를 함께 실행하여 SQL Server가 batch compile 시점에 새 컬럼을 인식하지 못한 것이었다.

최종 수정에서는 다음을 각각 별도 실행 batch로 분리하였다.

- ADD COLUMN
- FK/INDEX 생성
- legacy Contract Item 생성
- LOT link UPDATE

또한:
- FK 실제 존재검사
- INDEX 실제 존재검사
- 부분 적용 DB 대응
- 기존 Contract Item이 있는 계약/없는 계약 대응
- NULL LOT link 보정
- Migration 재실행 멱등성

을 보강하였다.

## 16. 계약조건과 실제 발생원가의 분리

매우 중요한 Phase 2 설계원칙이다.

**계약관리의 비용조건**은:

> 어떤 조건으로 거래하기로 계약했는가?

를 나타낸다.

**원가정산**은:

> 실제로 언제 얼마의 비용이 발생했는가?

를 나타낸다.

두 데이터를 혼합하지 않는다.

현재 화면의 공통 `조건 적용 시작일` 하나로 모든 실제 비용의 발생일을 대표해서는 안 된다.

비용은 최소한 다음 두 성격으로 구분한다.

### 16.1 Event / Actual Cost
건별 실제 발생비용.

예:
- L/C 개설비용
- 수입대금 지급
- BL 양수도금액 지급
- 통관비
- 검역비
- 최초 입고비
- 작업비
- 기타비용

각 건별로 필요에 따라:
- 실제 발생일
- 금액
- 통화
- 환율
- 세무속성
- 부담주체
- 설명/비고
- 근거/증빙

을 기록한다.

### 16.2 Period / Accrual Cost
기간에 따라 계속 발생하는 비용.

대표:
- Financing 이자
- 창고 보관료

각 비용은 자체 기산일과 종료기준을 가져야 한다.

예:
- 보관료: 실제 창고 입고일 → 해당 수량 출고일
- 이자: 계약상 기산일 → 회수/정산 기준일

따라서 모든 비용에 하나의 공통 시작일을 강제하지 않는다.

## 18. 수입원가정산서 설계 방향

원가정산 화면에서는 계약 및 기존 ERP에서 확보할 수 있는 정보를 최대한 자동으로 가져온다.

자동승계 후보:
- contract_id / contract_no
- 계약업체
- 계약상품
- 계약수량
- 계약조건
- BL
- Invoice
- 환율
- 통관자료
- ERP LOT
- 기타 기존 ERP 자료

원가정산서에는 기본 원가항목을 미리 제공하되, 실제 발생하지 않은 항목은 처리하지 않을 수 있어야 한다.

기본항목 예:
- 상품 수입대금
- L/C 개설비
- 금융비용
- 보험료
- 관세/통관비
- 검역비
- 운송비
- 최초 창고입고비
- 작업비
- 기타 기본비용

각 행에는 필요에 따라:
- 발생일
- 항목
- 자동/수동
- 통화
- 환율
- 금액
- +/- 구분
- 세무속성
- 부담주체
- 비고/근거

를 기록한다.

### 자유항목
기본항목과 같은 구조의 자유항목을 사용자가 추가/삭제할 수 있어야 한다.

- 추가비용: `+`
- 할인
- 환급
- 비용감액
- 기타 조정: `-`

모두 표현할 수 있어야 한다.

원가정산 확정결과는 향후:
- 총 실제원가
- 총 수량/KG
- KG당 실제원가
- 필요 시 상품별/LOT별 배부원가

등을 산출하여 출고정산의 원가기준으로 사용한다.

## 19. 3종 계약서 자동작성

정형화된 계약서 3개 유형을 시스템화한다.

현재 예정:
1. 수입대행계약
2. BL 양수도계약
3. 국내매입계약

실제 현재 사용하는 계약서 원본을 기준으로 Template을 설계한다.

계약관리에서 확보한 변수는 자동으로 삽입한다.

예:
- 계약번호
- 계약일
- 회사/계약주체 정보
- 계약업체 상호
- 대표자
- 사업자번호
- 주소
- 상품정보
- 원산지
- 수량
- 단가/금액
- 이자조건
- 중개수수료
- 보증금
- 비용부담
- 기타 계약조건

업무흐름:

```text
계약정보
→ 계약서 Template 선택
→ 변수 자동입력
→ 계약서 자동작성
→ 사용자 수동수정 가능
→ 계약서 확정
→ PDF/출력
→ 확정본 보존
```

Template과 실제 계약서 Snapshot은 분리한다.

향후 Template 문구가 변경되어도 과거 확정 계약서가 변경되어서는 안 된다.

필요 개념:
- DRAFT / CONFIRMED
- Version
- 작성자
- 수정자
- 확정자
- 확정일
- Audit

계약조건 변경으로 계약서 변경이 필요한 경우 기존 확정본을 덮어쓰지 않고 **변경계약서/추가약정서 새 Version**으로 관리한다.

특별출고약정서도 향후 같은 문서체계에 포함할 수 있다.

## 20. 전체 Financing 업무 Pipeline

앞으로 5개 주요 기능을 각각 독립된 프로그램처럼 만들지 않는다.

**하나의 계약 데이터가 다음 단계로 계속 승계되는 업무 Pipeline**으로 설계한다.

### 1단계 — 계약관리
계약업체, 상품, 수량, 계약조건, 책임, 보증금, 특별약정 등을 확정한다.

↓

### 2단계 — 계약서 작성
계약관리 확정정보를 자동승계한다.

3종 Template 중 계약유형에 맞는 계약서를 자동작성하고, 필요한 경우 사용자가 수정한 뒤 Snapshot으로 확정한다.

↓

### 3단계 — 실제 매입/수입/통관/입고
기존 MXMN 매입 및 ERP System of Record를 사용한다.

↓

### 4단계 — 수입원가정산
계약관리 및 기존 ERP 자료를 자동승계한다.

실제 발생한 건별 원가와 +/- 자유항목을 추가하고 실제 원가를 확정한다.

↓

### 5단계 — ERP LOT 연결
```text
Contract
→ Contract Item
→ ERP LOT
```

↓

### 6단계 — Financing 기간비용 계산
확정원가와 계약조건을 기준으로:
- 이자
- 보관료
- 수수료
- 기타 기간비용

을 계산한다.

↓

### 7단계 — 일일/부분출고 정산
출고일마다:
- 실제 출고업체
- LOT
- BOX/KG
- 배부 원가
- 경과기간
- 이자
- 보관비
- 수수료
- 물류/부대비용
- +/- 조정

을 계산한다.

↓

### 8단계 — 회수유형 적용
계약에서 확정한 회수유형을 적용하여 최종 출고가를 산출한다.

↓

### 9단계 — 일일 입금요청서
확정된 출고정산 결과에서 당일 입금요청금액과 입금요청서를 자동 생성한다.

↓

### 10단계 — 입금확인
실제 은행입금을 확인한다.

ERP RECEIPT 등록시점과 실제 은행입금 확인시점은 다를 수 있다.

↓

### 11단계 — 기존 ERP SALE/OUTBOUND 자동연계
확정된 출고정산의 다음 값을 기존 ERP로 전달한다.

- 실제 출고업체
- LOT
- BOX/KG
- 확정 출고단가/금액
- 창고
- 비고
- contract_id
- 정산 식별자

기존 MXMN의:

```text
SALE
→ OUTBOUND
→ LOT 재고반영
→ 매출채권
→ 거래처원장
```

흐름을 그대로 사용한다.

↓

### 12단계 — 일일 출고 거래명세표 발생/전송
기존 SALE 데이터를 기반으로 거래명세표를 자동 생성한다.

향후:
- PDF
- 인쇄
- 이메일 등 전송

기능과 연결한다.

거래명세표의 거래상대방은 최초 계약업체가 아니라 **실제 출고업체**이다.

↓

### 13단계 — 반복 부분출고
계약 전체에서 다음을 누적 추적한다.

- 계약수량
- 입고수량
- LOT 배정량
- 누적 출고량
- 잔량
- 누적 원가회수
- 누적 이자회수
- 누적 비용회수
- 보증금
- 미정산사항

↓

### 14단계 — 최종정산/마감
재고가 0이라고 계약을 자동 CLOSED 처리하지 않는다.

최종적으로:
- 전체 원가
- 전체 출고
- 전체 이자
- 전체 비용
- +/- 조정
- 전체 입금
- 보증금
- 보증금 반환/재배정
- 누락비용
- 중복회수
- 잔여정산

을 검증한 뒤 계약을 CLOSED 처리한다.

## 21. 가장 중요한 자동연동 원칙

**앞 단계의 확정 결과는 다음 단계의 자동 입력값이 된다.**

```text
계약 확정
→ 계약서 자동작성

계약 + 실제 수입자료
→ 원가정산 자동작성

확정원가 + 계약조건 + LOT + 날짜
→ 출고정산 자동계산

확정 출고정산
→ 일일 입금요청서 자동작성

입금확인 + 확정 출고정산
→ 기존 SALE/OUTBOUND 자동연계

SALE
→ 거래명세표 자동발행/전송
```

같은 업체, 상품, 수량, LOT, 가격, 계약번호, BL 등의 정보를 단계마다 다시 입력하지 않는 것이 원칙이다.

## 22. 자동승계와 Snapshot의 구분

자동승계는 편의를 위한 것이지만, 확정된 업무문서는 당시 값을 보존해야 한다.

예:
- 확정 계약서
- 확정 원가정산서
- 확정 일일출고정산
- 확정 입금요청서
- 확정 거래명세표

상위 Master나 계약조건이 나중에 변경되어도 과거 확정 문서와 정산결과가 자동으로 변경되어서는 안 된다.

수정이 필요한 경우:
- Version
- 수정사유
- 변경 전/후
- 작성자
- 수정자
- 확정자
- 일시

를 Audit/History로 남긴다.

## 23. Phase 2 개발 전 반드시 먼저 할 설계

Phase 2를 바로 코딩하지 않는다.

먼저 다음 5개 기능의 **논리적 데이터 흐름**을 하나의 설계로 확정한다.

1. 계약관리
2. 계약서 작성
3. 수입원가정산
4. 일일 출고정산/입금요청
5. SALE/OUTBOUND/거래명세표

각 단계마다 반드시 다음을 구분한다.

- 앞 단계에서 자동승계되는 데이터
- 사용자가 직접 입력하는 데이터
- 시스템이 계산하는 데이터
- 확정 데이터
- Snapshot
- 수정/취소 규칙
- Audit
- 다음 단계로 전달되는 데이터

특히 **원가정산과 출고정산의 Domain/Data Model을 먼저 확정한 뒤 구현**한다.
