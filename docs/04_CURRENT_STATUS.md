## 1. 현재 개발 위치

MXMN은 현재 **ERP Framework 구축 이후 MASTER 영역의 거래처관리 Vertical
Slice를 구현·검증하는 단계**이다.

기본 실행 구조는 다음과 같다.

`PySide6 Client → HTTP → FastAPI → SQLAlchemy / pyodbc → MS SQL Server (mxmn_dev)`

현재 개발은 기존 정상 기능을 유지하면서 작은 기능 단위로 수정하고, 실제
실행 검증 후 Git Commit하는 방식으로 진행한다.

## 2. 현재까지 정상 작동 확인

### 2.1 개발환경 / DB / API

-   Windows + Python 3.11+ 가상환경 `.venv`
-   MS SQL Server 2025 Express / DB `mxmn_dev`
-   SQLAlchemy + pyodbc DB 연결
-   FastAPI 서버 실행
-   PySide6 Desktop Client 실행
-   로그인 → Main Window 진입
-   업무회사 선택 및 변경
-   Git / GitHub 기반 소스 버전관리

### 2.2 FastAPI 시작 지연 조치

기존 `main.py`에서 서버 시작 시 실행되던 아래 코드는 현재 주석
처리하였다.

`Base.metadata.create_all(bind=engine)`

DB 구조는 Migration으로 관리하므로 FastAPI 실행 때마다 전체 Metadata를
확인/생성하지 않는 방향으로 전환하였다. 이 조치 후 FastAPI 시작 지연이
크게 줄었다.

### 2.3 SQL Server 일시 응답불능 문제

2026-09-15 개발 중 다음 현상이 발생하였다.

-   1433 Port는 `TcpTestSucceeded : True`
-   FastAPI 자체는 정상 기동
-   pyodbc 직접연결은 Login Timeout
-   SSMS에서도 `127.0.0.1,1433` 접속 Timeout
-   `MSSQL$SQLEXPRESS` 서비스는 Running으로 표시

`MSSQL$SQLEXPRESS` 서비스를 재시작한 후 SSMS 및 프로그램 연결이
정상화되었다.

따라서 동일 증상 발생 시 **Python/FastAPI 코드를 먼저 수정하지 말고 SQL
Server 실제 응답상태를 먼저 점검**한다.

## 3. 거래처관리 현재 구현 상태

### 3.1 거래처 Master

현재 거래처 공통 Master와 업무회사별 거래처 관계를 분리하여 관리한다.

주요 구현/확인 사항:

-   거래처 조회
-   신규 등록
-   수정 / 저장
-   거래처코드 자동발번
-   거래처명 필수
-   사업자번호
-   법인번호
-   대표자
-   우편번호 / 주소
-   업태 / 업종
-   전화 / 팩스
-   담당자
-   전자(세금)계산서 이메일
-   계좌정보
-   공통 메모
-   Enter 중심 입력항목 이동

### 3.2 거래처 화면 간소화

실무 검토 결과 다음 방향으로 정리하였다.

-   좌측 거래처 목록은 **거래처명을 가장 먼저, 충분한 폭으로 표시**
-   담당자 휴대폰: 화면에서 제거
-   은행명 / 계좌번호 / 예금주: **계좌정보 한 칸으로 통합**
-   축산물이력제 거래처번호: 현재 화면에서 제거
-   상세주소 별도 입력: 제거하고 주소 한 칸으로 사용
-   전자(세금)계산서 이메일: 한 개만 사용
-   기존 DB 컬럼은 불필요하게 DROP하지 않고 호환성을 위해 유지 가능

### 3.3 업무회사별 거래정보

거래처 공통정보와 별도로 회사별 관계정보를 관리한다.

현재 주요 항목:

-   거래상태: 거래처 / 정보등록만
-   업무유형
    -   일반
    -   계약
    -   유통
    -   BL양수도
    -   보증금
    -   기타
-   매입거래 여부
-   매출거래 여부
-   (세금)계산서 발행대상 여부
-   거래중단 여부

`거래중단`은 단순한 정보등록 여부와 다른 개념이다. 거래중단된 업체는
일반 매입/매출 거래처 조회에서 기본적으로 보이지 않게 하고, 필요 시
`거래중단 포함`으로 조회한다.

## 4. 거래처명 사용에 관한 실무 기준

동일 법적 사업자라도 업무상 역할을 구분하기 위해 복수의 ERP 거래처코드를
사용할 수 있다.

예:

-   `(계약)(주)제이케이미트코퍼레이션`
-   `(유통)(주)제이케이미트코퍼레이션`
-   `(BL양수도)(주)제이케이미트코퍼레이션`
-   `(보증금)(주)제이케이미트코퍼레이션`

이는 장기 목표인 **법적 사업자(Partner)와 업무 거래처코드(Customer)의
분리**와 연결되는 실무 요구사항이다.

별도의 `계약서 거래처명` 필드를 중복 관리하기보다는 실제 거래처명과 향후
Partner의 법적 상호를 적절히 분리하는 방향으로 발전시킨다.

## 5. (세금)계산서 발행 설계 원칙

거래처 화면에서는 단순하고 직관적으로 다음 설정을 사용한다.

`□ (세금)계산서 발행대상`

단, 실제 계산서 발행은 거래처 설정만으로 판단하지 않는다.

### 중복발행 방지 원칙

월중 여러 건의 거래명세서를 발행하는 거래처가 특정 거래에 대해
거래명세서와 함께 단건 계산서 발행을 요청할 수 있다.

따라서 월말 합산발행 시:

1.  해당 월의 계산서 발행대상 매출을 조회
2.  이미 단건 계산서에 포함된 원거래를 확인
3.  단건 발행 완료 거래는 월합산 대상에서 제외
4.  남은 미발행 거래만 합산
5.  월합산 계산서 생성
6.  계산서와 포함된 원거래 간 연결관계를 저장

**중복방지는 금액 차감 방식이 아니라 원거래 ID와 계산서 발행이력의
연결관계로 관리한다.**

향후 `tb_tax_document` 및 관련 Detail/Link 구조 설계 시 이 원칙을
반영한다.

### 거래처 화면

-   단축메뉴 `코드관리 → 거래처입력` 연결

### 서버 / DB

-   FastAPI 시작 지연
-   SQL Server Login Timeout
-   SQLEXPRESS 서비스 Running 상태의 실제 응답불능

현재 위 문제들은 조치 후 정상 작동을 확인하였다.
