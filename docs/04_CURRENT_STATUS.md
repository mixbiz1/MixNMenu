## 1. 현재 개발 위치

MXMN은 MASTER 영역의 **거래처·공통코드·상품공통코드·계층형 상품분류·
상품·창고·LOT·계층형 경비코드 Vertical Slice를 구현**하였다.

최초재고와 거래처 최초잔액을 등록하는 `초기자료등록` 1차도 구현하였다.
현재 다음 큰 업무 단계는 일반 매입·입고·재고·매출·출고 및 수금·지급
Transaction 연결이며, 경비코드는 향후 거래 Detail과 손익·경비통계
Report에 FK로 연결한다.

경비코드는 `그룹 / 실제입력 / 자동계산`으로 분리하였고, 표준 손익 최상위
구조와 세전·예상 법인세·세후 손익 항목을 시스템이 자동 생성한다.

기본 실행 구조는 다음과 같다.

`PySide6 Client → HTTP → FastAPI → SQLAlchemy / pyodbc → MS SQL Server (mxmn_dev)`

현재 개발은 기존 정상 기능을 유지하면서 작은 기능 단위로 수정하고, 실제
실행 검증 후 Git Commit하는 방식으로 진행한다.

-   업무회사 선택 및 변경
-   Git / GitHub 기반 소스 버전관리

### 2.2 FastAPI 시작 지연 조치

기존 `main.py`에서 서버 시작 시 실행되던 아래 코드는 현재 주석
처리하였다.

`Base.metadata.create_all(bind=engine)`

DB 구조는 Migration으로 관리하므로 FastAPI 실행 때마다 전체 Metadata를
확인/생성하지 않는 방향으로 전환하였다. 이 조치 후 FastAPI 시작 지연이
크게 줄었다.

### 2.3 SQL Server 일시 응답불능 문제

2026-09-15 개발 중 다음 현상이 발생하였다.

-   1433 Port는 `TcpTestSucceeded : True`
-   FastAPI 자체는 정상 기동
-   pyodbc 직접연결은 Login Timeout
-   SSMS에서도 `127.0.0.1,1433` 접속 Timeout
-   `MSSQL$SQLEXPRESS` 서비스는 Running으로 표시

`MSSQL$SQLEXPRESS` 서비스를 재시작한 후 SSMS 및 프로그램 연결이
정상화되었다.

따라서 동일 증상 발생 시 **Python/FastAPI 코드를 먼저 수정하지 말고 SQL
Server 실제 응답상태를 먼저 점검**한다.

-   계좌정보

### 3.2 거래처 화면 간소화

실무 검토 결과 다음 방향으로 정리하였다.

-   좌측 거래처 목록은 **거래처명을 가장 먼저, 충분한 폭으로 표시**
-   담당자 휴대폰: 화면에서 제거
-   은행명 / 계좌번호 / 예금주: **계좌정보 한 칸으로 통합**
-   축산물이력제 거래처번호: 현재 화면에서 제거
-   상세주소 별도 입력: 제거하고 주소 한 칸으로 사용
-   전자(세금)계산서 이메일: 한 개만 사용
-   기존 DB 컬럼은 불필요하게 DROP하지 않고 호환성을 위해 유지 가능

### 3.3 업무회사별 거래정보

거래처 공통정보와 별도로 회사별 관계정보를 관리한다.

현재 주요 항목:

-   거래상태: 거래처 / 정보등록만
-   업무유형
    -   일반
    -   계약
    -   유통
    -   BL양수도
    -   보증금
    -   기타
-   매입거래 여부
-   매출거래 여부
-   (세금)계산서 발행대상 여부
-   거래중단 여부

`거래중단`은 단순한 정보등록 여부와 다른 개념이다. 거래중단된 업체는
일반 매입/매출 거래처 조회에서 기본적으로 보이지 않게 하고, 필요 시
`거래중단 포함`으로 조회한다.

## 4. 거래처명 사용에 관한 실무 기준

동일 법적 사업자라도 업무상 역할을 구분하기 위해 복수의 ERP 거래처코드를
사용할 수 있다.

예:

-   `(계약)(주)제이케이미트코퍼레이션`
-   `(유통)(주)제이케이미트코퍼레이션`
-   `(BL양수도)(주)제이케이미트코퍼레이션`
-   `(보증금)(주)제이케이미트코퍼레이션`

이는 장기 목표인 **법적 사업자(Partner)와 업무 거래처코드(Customer)의
분리**와 연결되는 실무 요구사항이다.

별도의 `계약서 거래처명` 필드를 중복 관리하기보다는 실제 거래처명과 향후
Partner의 법적 상호를 적절히 분리하는 방향으로 발전시킨다.

## 5. (세금)계산서 발행 설계 원칙

거래처 화면에서는 단순하고 직관적으로 다음 설정을 사용한다.

`□ (세금)계산서 발행대상`

단, 실제 계산서 발행은 거래처 설정만으로 판단하지 않는다.

### 중복발행 방지 원칙

월중 여러 건의 거래명세서를 발행하는 거래처가 특정 거래에 대해
거래명세서와 함께 단건 계산서 발행을 요청할 수 있다.

따라서 월말 합산발행 시:

1.  해당 월의 계산서 발행대상 매출을 조회
2.  이미 단건 계산서에 포함된 원거래를 확인
3.  단건 발행 완료 거래는 월합산 대상에서 제외
4.  남은 미발행 거래만 합산
5.  월합산 계산서 생성
6.  계산서와 포함된 원거래 간 연결관계를 저장

**중복방지는 금액 차감 방식이 아니라 원거래 ID와 계산서 발행이력의
연결관계로 관리한다.**

향후 `tb_tax_document` 및 관련 Detail/Link 구조 설계 시 이 원칙을
반영한다.

### 8.1 화면 초기조회 및 사용자 반응 원칙

코드관리·거래처입력·상품공통코드·상품입력 화면은 초기 API/DB 조회가
완료될 때까지 창 표시가 늦어지는 구조를 개선하였다.

2026-09-16 사용자 실행검증 결과:

-   메뉴 클릭 후 화면 포맷이 먼저 표시됨
-   데이터가 뒤이어 채워져 프로그램이 반응 중임을 확인할 수 있음
-   거래처 및 상품공통코드의 독립 API 요청 병렬화 적용
-   기존 기능 오류 없음

앞으로 데이터 조회가 있는 모든 화면에는 다음 원칙을 공통 적용한다.

1.  메뉴 클릭 시 화면을 먼저 표시한다.
2.  초기 데이터는 화면 표시 이후 조회한다.
3.  독립적인 API 요청은 안전한 범위에서 병렬 처리한다.
4.  조회 중에는 버튼을 `조회 중...`으로 표시하고 중복 입력을 차단한다.
5.  완료 또는 오류 발생 시 버튼과 입력 상태를 반드시 복원한다.
6.  장시간 조회는 공통 Background Worker/QThread 구조로 단계적으로 전환한다.
7.  조회·저장 로직과 화면 갱신은 분리하여 UI 스레드 안전성을 유지한다.

2차 개선으로 코드관리·거래처입력·상품공통코드·상품입력 조회 버튼의
`조회 중...` 상태 표시 및 중복 실행 차단을 적용하였다.

## 21. 초기자료등록 Vertical Slice 1차 구현 (2026-09-17)

### 21.1 메뉴와 화면

- 코드관리의 기존 단일 `거래처 기초잔액 입력` 자리에는
  `8.초기자료등록` 상위 메뉴를 배치하였다.
- 하위 메뉴는 `1.최초재고 등록`, `2.거래처 최초잔액 등록`이다.
- 최초재고 화면은 회사·기준일·창고 Header와 복수 Detail 행을 입력한다.
- Detail은 상품·수입/국내매입·공급자 LOT·BL·컨테이너·이력번호·원산지·
  EST·생산일·소비기한·BOX·KG·개별원가·메모를 지원한다.
- 거래처 최초잔액 화면은 기준일·미수/미지급·거래처·금액·메모를 입력하고,
  이미 등록한 원거래의 최초금액·배분금액·미결잔액을 조회한다.

### 21.2 원장과 원자성

- `tb_inbound`, `tb_inbound_item`을 추가하였다.
- 최초재고 저장 시 입고 Header, 각 LOT, 각 입고 Detail을 단일 DB
  Transaction에서 생성하며 오류 시 전체 Rollback한다.
- 재고수량은 LOT Master에 저장하지 않고 입고 Detail의 BOX·KG를 원본으로
  사용한다.
- `tb_account_transaction`에 최초 미수금과 최초 미지급금을 각각 독립된

## 25. LOT 소비기한 자동계산·목록 정렬 원칙 (2026-09-17)

- LOT 조회/보정에서 상품 또는 생산일을 변경하면 상품 Master의 소비기한
  규칙을 즉시 다시 적용한다.
- `AUTO` 상품은 냉장으로 명시된 경우를 제외하고 일반 수입 냉동육 기본값인
  생산일 + 2년 - 1일을 적용한다.
- 냉장육·특정 브랜드는 상품 Master의 `DAYS` 또는 `NONE` 규칙으로 예외를
  명시한다.
- 자동계산된 소비기한은 특별한 사유가 있으면 LOT 화면에서 수동 보정할 수
  있으며, 단순 조회만으로 기존 수동 보정값을 덮어쓰지 않는다.
- LOT 목록은 열 제목 클릭 시 오름차순·내림차순을 전환한다. 정렬 후에도
  화면행이 아닌 LOT ID를 기준으로 선택·수정한다.
- 앞으로 신규 또는 개선하는 조회목록은 제목 클릭 정렬을 기본원칙으로 하며,
  날짜·숫자·금액은 표시문자가 아닌 실제 값 기준으로 정렬한다.

## 29. 공통코드 선택 보정·경비코드 Master 구현 (2026-09-17)

### 29.1 공통코드 상세행 선택 보정

-   상세코드 표의 어느 셀을 클릭해도 해당 행 전체를 선택하고 첫 열에 보관한
    `code_value_id`를 편집·사용중지 대상으로 확정한다.
-   표시 정렬 후에도 행번호가 아니라 고유 ID를 사용하므로 다른 상세코드를
    수정하거나 사용중지할 위험을 만들지 않는다.

### 29.2 계층형 경비코드

-   상품분류나 일반 공통코드와 분리된 `tb_expense_code` Master를 추가하였다.
-   `expense_id` 내부 PK, `E00001` 형식 업무코드 UNIQUE,
    `parent_expense_id` Self FK 구조이다.
-   최대 4단계이며 매출·매입/매출원가·판매관리비·영업외수익·영업외비용
    손익구분을 지원한다. 하위코드는 상위코드의 손익구분을 자동 상속하고,
    최상위 손익구분 수정 시 모든 하위코드도 같은 Transaction에서 변경한다.
-   최상위 신규·하위코드 추가·수정·조회·사용중지 CRUD를 구현하였다.
-   상위 변경 시 하위코드가 있으면 변경을 차단하고, 사용중지는 선택 코드와
    모든 하위코드에 함께 적용한다. 물리삭제는 하지 않는다.
-   `2.코드관리`에 `5.경비코드입력`을 추가하고 이후 메뉴를

    순차 변경하였다.
-   단축메뉴에는 경비코드입력을 다시 추가하지 않았다.

## 20. LOT Master 1차 완료 (2026-09-17)

### 20.1 설계 확정

-   LOT는 상품의 입고분을 식별하는 추적 Master이며 재고수량 장부가 아니다.
-   회사별 업무 표시번호는 `LYYYYMMDD-001` 형식으로 자동발번한다.
-   수입 LOT와 국내매입 LOT를 같은 테이블에서 `source_type`으로 구분한다.
-   회사·상품·최초 입고 예정창고를 연결하고 공급자 LOT번호·BL·컨테이너·축산물
    이력번호·원산지·EST·생산일·소비기한을 관리한다.
-   원가는 원/KG 기준 LOT별 개별원가로 관리하고 평균원가는 사용하지 않는다.
    가격·개별원가는 정수 원 단위로 표시하며 소수점 이하는 올림한다.
-   동일 BL의 복수 컨테이너, 같은 컨테이너의 복수 상품·이력번호는 LOT를
    분리한다.
-   LOT 상태는 사용중·보류·마감으로 구분하며 사용중지는 물리삭제하지 않는다.
-   입고 BOX·KG 및 현재고는 후속 입고/출고 Transaction으로 관리한다.
-   창고이동 후 실제 재고위치는 LOT의 창고값을 덮어쓰지 않고 Transaction으로
    산출한다.

### 20.2 구현 파일

-   `models.py`: `Lot` ORM 추가
-   `db_lot_migrate.py`: `tb_lot` 비파괴 Migration 추가
-   `main.py`: 회사별 LOT 조회·생성·수정·사용중지·안전삭제 API 추가
-   `views/lot_reg.py`: LOT조회/보정 Pure Python PySide6 화면 추가
-   `views/mxmn_main_window.py`: 코드관리 `8.LOT조회/보정` 메뉴 연결

### 20.3 검증 결과

-   사용자 Windows 환경에서 LOT 화면 정상 표시 확인
-   Python 문법검사와 FastAPI LOT Route 로딩 통과
-   PySide6 Offscreen 화면 생성 및 버튼상태 검증 통과
-   LOT 수동 신규등록 제거
-   연결자료 없는 LOT만 삭제하고 연결자료가 있으면 DB FK로 차단
-   기존 상품·창고·거래처 기능 변경 없음

### 20.4 사용자 1차 실행검토 반영

LOT 화면 정상 표시를 확인한 뒤 업무구조를 다음과 같이 수정하였다.

-   LOT는 기초코드처럼 독립 신규등록하지 않는다.
-   `LOT입력` 화면을 `LOT조회/보정`으로 변경하고 수동 신규 버튼을 제거한다.
-   최초재고·매입입고·수입입고 저장 시 LOT가 원인 Transaction과 함께
    생성되도록 한다.
-   연결자료가 없는 임시/오입력 LOT에는 2회 확인 후 실제 삭제를 허용한다.
-   입고·출고·재고 등 외래키 연결자료가 있으면 DB 제약 오류를 API에서
    처리하여 물리삭제를 차단한다.
-   시스템 최초 도입자료는 `초기자료등록` 업무로 분리한다.
    - 최초재고: LOT 추적정보 + BOX + KG + 개별원가
    - 거래처별 미수·미지급 최초잔액
    - 통장/현금별 최초잔액
-   초기자료 입력 후 재고와 잔액은 매입·매출·입고·출고·이동·수금·지급
    Transaction의 논리적 결과로만 계산한다.

다음 구현 순서는 일반 매입·입고·재고조회 Transaction을 연결한 뒤
매출·출고와 수금·지급 Allocation으로 확장하는 것이다. 경비코드는 실제
거래 Detail이 구현될 때 FK로 연결하며, Master 단계에서 별도 잔액이나
금액을 저장하지 않는다.

### 20.5 수치 정밀도 확정

-   가격·단가·LOT 개별원가: 소수점 없이 원 단위, 소수점 이하는 올림
-   중량: KG 소수점 둘째 자리까지 (`256.37kg`)
-   BOX: 정수
-   환율: 소수점 둘째 자리까지

LOT 조회/보정 화면의 개별원가는 소수점 없는 정수로 변경했고, API에서도
입력값을 원 단위로 올림하여 저장한다. `tb_lot.individual_cost`의 기존
Scale은 호환성을 위해 변경하지 않고 Application Rule로 정수값을 보장한다.

## 30. 표준 손익·경비코드 구조 개편 (2026-09-18)

### 30.1 표준구조 자동 생성

-   시스템이 `매출`, `매출원가`, `매출총이익`, `판매비와관리비`,
    `영업이익`, `영업외수익`, `영업외비용`, `법인세비용차감전순이익`,
    `법인세비용(예상)`, `당기순이익(예상)`의 최상위 10개 항목을 생성한다.
-   매출총이익·영업이익·세전이익·예상 법인세·예상 당기순이익은
    `CALCULATED` 항목이며 거래 입력용으로 선택하지 않는다.
-   표준 최상위 항목은 수정·삭제·사용중지할 수 없다.
-   `GROUP`과 `INPUT` 일반항목 아래에 하위항목을 최대 4단계로 추가할 수
    있으며 손익구분은 상위항목에서 자동 상속한다. 거래 입력 화면에서는
    하위항목이 없는 최하위 `INPUT`만 선택 대상으로 사용한다.

### 30.2 직관적 입력과 삭제 원칙

-   화면명을 `손익·경비코드 입력`으로 정리하고 트리에
    `[그룹]`, `[실제입력]`, `[자동계산]`과 선택 항목의 전체 경로를 표시한다.
-   `새로고침 [F7]`과 `취소 [F5]`를 제공한다. 지급수수료와 같은 일반
    입력항목에도 용차료·택배비·강사료 등의 하위항목을 추가할 수 있다.
-   사용 이력이 없는 사용자 항목은 하위항목과 함께 물리 삭제한다.
-   향후 거래 FK에 연결된 항목은 물리삭제 실패 시 자동 사용중지하여
    과거 자료의 참조 무결성을 보존한다.
-   `표준구조 재생성`은 명시적 확인 후에만 실행하며, 연결 자료가 있으면
    FK 제약으로 중단한다.

### 30.3 DB·API·Migration

-   `tb_expense_code`에 `node_type`, `formula_code`, `system_yn`을 추가하였다.
-   표준 42개 항목은 `expense_code_defaults.py` 한 곳에서 관리한다.
-   Migration은 시스템 표준항목이 없는 1차 시험 DB를 1회 표준구조로
    전환한다. 현재 이 Master를 참조하는 거래 Detail은 구현 전이므로 기존
    시험자료를 대체하며, 이후 재실행에서는 사용자 하위항목을 유지한다.
-   빈 DB의 경비코드 조회 시에도 표준구조를 자동 생성한다.
